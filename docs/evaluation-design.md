# Evaluation design

This document describes how the evaluation is set up and why. It deliberately
does not restate result values: those live in the result files under
`artifacts/analysis/results/` and in the generated tables under
`reports/paper_figs_v2/`, and duplicating them here is how documentation and
findings drift apart.

## The shape of the problem

N = 120 records, 19 predictors, and an outcome that is itself an estimate rather
than a measurement. That combination makes three failure modes worth guarding
against explicitly: overfitting, leakage across the split, and reading noise as
signal across five simultaneous tests.

## Estimator

```
SimpleImputer(median) -> StandardScaler -> Ridge
```

Ridge rather than OLS because several features are correlated by construction
(`PG_pause_mean` / `p50` / `p90` measure the same distribution at different
points). Imputation and scaling sit inside the pipeline, so both are fitted on
training folds only; doing either before the split would leak test-fold
information through the median and the standardisation constants.

`alpha = 100`, fixed. A permutation test needs the estimator held constant
across permutations: if `alpha` were re-selected by inner CV on each permuted
outcome, the null distribution would be generated by a different estimator each
time and the p-value would no longer refer to a single hypothesis. The value is
close to what `RidgeCV` over a 25-point grid selects on the observed data, and
its influence is checked in the alpha sensitivity analysis.

## Cross-validation: subject-wise

```python
GroupKFold(n_splits=5)   # groups = cejc_person_id
```

74 unique speakers produce the 120 records, and 25 speakers appear in more than
one conversation. A plain `KFold` would place two records from the same speaker
on opposite sides of the split, which inflates performance for a model whose
predictors are speaker-level habits. Grouping on `cejc_person_id` prevents that.

`speaker_id` cannot be used for grouping: in CEJC it is a within-conversation
label (`IC01`, `IC02`, ...), so the same string refers to different people in
different conversations. Person identity comes from the speaker metadata table.

An earlier version of the analysis used `KFold`. `make groupkfold-compare` runs
both across all trait x model combinations and writes the comparison, so the
size of the difference is on the record rather than asserted.

## Permutation test

```
r_obs   = corr(y, out-of-fold prediction of y)
repeat 5000 times:
    y*      = random permutation of y          # X untouched
    r_perm  = corr(y*, out-of-fold prediction of y*)
p = (count(|r_perm| >= |r_obs|) + 1) / (n_perm + 1)
```

Points that matter:

- **Only the outcome is permuted.** Permuting `X` would destroy the correlation
  structure among predictors, which is not the null hypothesis being tested. The
  hypothesis is that the association between the feature set and the outcome is
  no better than chance.
- **The whole CV is inside the permutation loop.** Model fitting is refitted on
  each permuted outcome, so the null distribution absorbs the optimism of the
  fitting procedure itself rather than only the correlation step.
- **The fold assignment is held fixed** across permutations, so the only source
  of variation is the permutation.
- **Two-sided**, via `|r_perm| >= |r_obs|`.
- **The `+1` in numerator and denominator** keeps p away from exactly zero, which
  a finite permutation sample cannot justify (Phipson & Smyth, 2010). With
  n_perm = 5000 the smallest reportable p is 1/5001.

## Multiple comparisons

Five traits are tested on the same feature set, so p-values are corrected across
traits with the Holm-Bonferroni step-down procedure. Holm rather than
Bonferroni because it is uniformly more powerful with the same familywise error
control, and rather than FDR because the claim being made is about individual
traits, not about a proportion of discoveries.

Both raw and corrected p-values are reported. The correction is implemented in
`holm_correction()` in `scripts/analysis/ensemble_permutation.py` and covered by
`tests/test_holm_correction.py`.

## Which features carry the association

Two independent procedures, reported together rather than separately:

1. **Permutation test on each coefficient**
   (`scripts/analysis/permutation_coef_test.py`) — is this coefficient larger
   than it would be under a permuted outcome?
2. **Bootstrap coefficient stability**, 500 resamples
   (`scripts/analysis/bootstrap_variance.py`) — does the coefficient keep its
   sign and stay away from zero across resamples of the data?

They answer different questions and can disagree. A feature is treated as a
driver only when both agree; the intersection is what the manuscript reports.
Features that pass one test but not the other are reported as possible
contributors and not used to support conclusions.

## Incremental validity

Three nested models, in a fixed order: demographics (sex, age) -> plus
classical features -> plus novel features. The primary metric is pooled
out-of-fold R² with RMSE alongside, and the increment from stage 2 to stage 3 is
tested with a paired bootstrap over per-record squared errors.

Correlation r is reported too, but in an appendix table, because r is not a
proper scoring rule for an incremental-validity claim: it is invariant to
affine rescaling of the prediction and so cannot distinguish a model that is
better calibrated from one that merely covaries.

The honest reading of the stage 2 -> 3 increment is in the manuscript. Where the
increment is not significant, it is reported as not significant; the
contribution of the novel features is supported at the coefficient level
instead, and the figure generator deliberately does not shade bars in a way that
would imply significance the test does not show.

## Confound control

Sex and age are added as predictors and the analysis is rerun with the same
subject-wise split
(`scripts/analysis/confound_analysis_groupkfold.py`). The question is whether the
feature-outcome association survives, not whether the confounded model predicts
better.

## Sensitivity analyses

Three arbitrary choices in the feature definitions are varied
(`scripts/analysis/sensitivity_analysis.py`):

| Choice | Variants | What it tests |
|---|---|---|
| `gap_tol` | 6 values, 0.01–1.0 s | where the boundary between a real pause and annotation noise is drawn |
| yes/no lexicon | narrow, broad | how permissive the response-type classifier is |
| ne/yo matching | 3 rules | how the sentence-final particle context is identified |
| `alpha` | grid | how much the regularisation strength matters |

The point is not to find the best variant. It is to show whether the reported
association depends on a threshold that was chosen without strong justification.

## Seeds and determinism

`seed = 42` throughout (permutation, bootstrap, fold assignment), passed
explicitly rather than relying on global state. Given identical inputs and the
pinned library versions in `requirements.txt`, every analysis in this repository
reproduces exactly. The one exception is the model scoring step, for the reasons
in [data-availability.md](data-availability.md).

## Tests

`make test` runs unit and property-based tests (Hypothesis) covering the parts
where a silent error would not be visible in the output: Holm correction
ordering, the feature-exclusion logic, the p90 exclusion rule, permutation
coefficient bookkeeping, three-stage feature-set construction, speaker-overlap
counting, and the numerical-consistency checker. These need no corpus data.
